Reference manual · x86-64 · stable Rust · Limine

A minimal x86-64 kernel that runs isolated, unprivileged tasks which talk only by messages. Drivers, storage and attestation are ordinary tasks, and the system is fixed at build time.

How to read this

Part one explains each layer from scratch, for readers who haven't built an operating system before. Part two is the reference: what each subsystem does, its interfaces, and the tests that prove it. Part three is for working on the code, by people or by coding agents: commands, file locations, recipes, rules and fixes. Agents should start at 18. Agent quick reference or fetch llms.txt.

Part one: guide

1Introduction#

vanir-os is a small kernel written in stable Rust and booted by Limine. Its design follows Oxide's Hubris: a fixed set of tasks is declared at build time, each runs in its own address space in ring 3, and they cooperate through synchronous send/receive/reply messages. Things a larger kernel does internally, such as device drivers, restarting failed programs, storage and talking to a host, are separate tasks here.

The kernel provides:

  • serial output, GDT/TSS, IDT, and an ELF loader that enforces W^X
  • a page-table tree per process, with SMEP, SMAP and NX
  • a 100 Hz local APIC timer, round-robin preemption and CPU budgets
  • synchronous IPC with a per-task allowlist of who may send to whom
  • supervisor notifications and task restarts with generation-checked ids
  • PCI device grants, MSI-X interrupts and DMA regions for driver tasks
  • a kernel event log, signature checks on task images, and boot measurements into a TPM
  • notifications a task posts to another without waiting, and a supervisor-only halt

On top of that, as tasks: virtio console, vsock, block and network drivers; telemetry streamed to a host agent; TPM remote attestation; encrypted per-task storage whose key the host releases only to a boot it has attested; and TCP services behind separate data and management network stacks, with routing and draining between instances.

Static

No fork or exec. The manifest fixes every task, its budget and who it may talk to.

Isolated

Each task has its own page tables. A crash ends that task, not the system.

Mechanism, not policy

The kernel reports deaths; the supervisor task decides what to do.

Verifiable

Signed images, Secure Boot, measured boot and TPM quotes, all checked by tests.

3The layers, from scratch#

An operating system is a stack of layers, each depending on the one below. This part walks up the stack once, saying in plain terms what each layer is for and how vanir-os does it. The reference in part two goes into detail.

3.1The machine#

In plain terms

A computer is a processor that runs instructions from memory, plus devices (disk, network, serial port) it talks to through special addresses. When it powers on, it runs firmware burned into the board, which finds a boot loader on a disk, which loads the kernel into memory and jumps to it. From then on the kernel is in charge.

vanir-os runs in QEMU, which emulates the machine in software (TCG) or uses the host CPU's virtualization (KVM). The firmware is SeaBIOS or OVMF; the boot loader is Limine, which also loads every task's ELF file and signature as "modules" next to the kernel.

3.2Privilege#

In plain terms

x86 processors have privilege levels called rings. Code in ring 0 can do anything: change memory maps, talk to hardware, turn off interrupts. Code in ring 3 can't, and if it tries, the processor stops it and hands control to ring 0. The kernel runs in ring 0; programs run in ring 3. That's what keeps a buggy or hostile program from taking over the machine.

The kernel sets this up with a GDT (segment descriptors for each ring), a TSS (which stack to switch to when ring 3 traps into ring 0), and CPU features: SMEP stops the kernel running user code, SMAP stops it reading or writing user memory except inside explicit copy routines, NX marks data pages non-executable, and CR0.WP makes read-only pages read-only for the kernel too.

3.3Virtual memory#

In plain terms

Programs don't see physical memory directly. Every address they use goes through page tables, a tree the processor walks to translate a virtual address to a physical one, 4 KiB at a time. Each page also has permissions: present, writable, user-visible, executable. Give each program its own page tables and it can't even name another program's memory.

3.4Traps: syscalls, faults, interrupts#

In plain terms

There are three ways into the kernel. A syscall is a program asking for something on purpose (here, with the int 0x80 instruction). A fault is the processor reporting a mistake, such as touching unmapped memory. An interrupt is a device or timer asking for attention. All three save where the program was, switch to ring 0, and run a handler listed in the IDT.

The timer interrupt fires 100 times a second. It's how the kernel takes the CPU back from a task that never gives it up (preemption) and how it counts CPU budgets.

3.5Tasks and messages#

In plain terms

A task (or process) is a program with its own memory and saved registers. The kernel switches between them quickly so they seem to run at once. Isolated tasks still need to cooperate, so they send each other messages: a client sends a request and waits; the server receives it, does the work and replies. The kernel copies the bytes between their memories and checks who is allowed to talk to whom.

vanir-os declares every task in an app manifest. The kernel never creates tasks at run time; it can only restart one, when the supervisor task asks.

3.6Devices#

In plain terms

Software controls a device by writing to its registers, which appear as memory addresses (MMIO). Fast devices also read and write main memory themselves: DMA, direct memory access. When they finish, they raise an interrupt. A driver is the code that knows a device's registers and protocol.

Here a driver is an ordinary ring-3 task. The kernel maps only that device's registers into the driver, gives it a fixed DMA region, and turns the device's interrupts into messages. A crashing driver is just a crashing task.

3.7Trust: signatures, measurements, keys#

In plain terms

Isolation protects tasks from each other, but how do you know the right code is running at all? Each boot stage checks a signature on the next before running it. Each stage also measures (hashes) what it runs into a TPM, a small security chip that keeps a running hash it can't be made to forget. Later the TPM can sign a quote of those hashes, so a remote host can verify what booted. Only then does the host hand over secrets, such as the key that decrypts the disk.

5Memory and address spaces#

Physical memory is handed out in 4 KiB frames from Limine's memory map, with a free list so frames return when a task dies. The kernel reaches physical memory through the HHDM (Limine's direct map). Each task gets its own PML4; the kernel half is shared and supervisor-only.

Two software bits in page-table entries record ownership: DEVICE (bit 9, MMIO, never freed) and PINNED (bit 10, DMA frames owned by the task slot, kept across restarts). Everything else a task maps is freed when it dies; the no-leak and restart-no-leak tests check the frame count returns to its baseline.

The kernel touches user memory only through copy_from_user and friends, which open a SMAP window (stac/clac) and recover from page faults through an exception table, so a bad pointer in a syscall returns an error instead of crashing the kernel.

6Tasks and scheduling#

  • Static task table. The tasks are fixed at build time by an app manifest (7). Tasks get ids 1, 2, … in manifest order.
  • One kernel stack. A trap saves the user's registers on it. A context switch stores that frame in the current task, copies the next task's saved frame over it, switches CR3, and returns through the normal iretq. Kernel code never waits in the middle of a syscall: a task that must wait is marked blocked with its registers saved, and whoever completes the operation writes the results into those saved registers.
  • Round-robin preemption on the 100 Hz timer. A task with a budget is killed after that many ticks of CPU.
  • Outcomes. A task ends by exit, by faulting, or by using up its budget; the others keep running. When nothing can run, the kernel prints a summary and halts with a status (20). Tasks waiting in recv count as idle servers; tasks stuck in send mean a deadlock.

7App manifests#

An app manifest is a TOML file listing every task. kernel/build.rs turns it into the kernel's task table at build time. Pick one with make run APP=… (default apps/default.toml; tests use tests/apps/).

name = "client"        # unique task name; also the program, unless `program` is set
program = "hello"      # optional: build/<program>.elf (any program under user/)
budget = 50            # optional: CPU budget in 10 ms ticks (default: unlimited)
supervisor = true      # optional: told when other tasks die (at most one)

dma_pages = 16         # optional: contiguous DMA region in 4 KiB pages (max 256)
events = true          # optional: may read the kernel event log and stats (at most one)
min_version = 2        # optional: refuse images signed with an older version
tpm = true             # optional: gets the TPM mapped, for attestation (at most one)
listen = [{ port = 80, max_connections = 64, max_per_source = 16 }]
                       # optional: TCP ports it may listen on (max_connections default 64,
                       # max_per_source default max_connections; at most 8 entries)
service = "web"        # optional: the network service it is an instance of (default: its name)
routes = true          # optional: may route, drain and blocklist in the network stacks

The build fails on unknown keys, duplicate names, unknown sends targets or device names, more than one supervisor, event reader, TPM task or loader, more than 64 tasks and slots, or a port declared by two different services (instances of one service may share it). Each devices entry claims the next unclaimed device of that kind; a missing device is logged and the task runs without it.

8IPC#

Synchronous send/receive/reply, as in Hubris. A client's send waits until the server has received the message and replied. The kernel copies messages and replies between address spaces, up to 4 KiB each. A task may only send to the tasks listed in its manifest sends.

Task ids carry a generation (slot + 1 | generation << 16) that changes on restart. A client holding an id from before a restart gets DEAD instead of silently reaching a fresh server that lost its state; it can lookup the name again and resend. Kernel notifications arrive as messages from sender 0.

9Supervisor#

One task may be marked supervisor = true (user/supervisor). The kernel reports every other task's death to it as a message from sender 0 with NOTIFY_DEATH and a death record: how it ended, exit code or fault vector, rip, cr2, error code and ticks used. The supervisor decides what to do and may call restart(id), which reloads the task's ELF into fresh memory with a new generation. The policy lives in the supervisor, not the kernel. If the supervisor itself dies, the kernel halts.

The policy (RFD 2, P5): a task that exits 0 is done. A task that faults, exits non-zero or uses up its CPU budget is always restarted, however often it crashes, so a request that crashes a service can't take it down for good. Restarts back off so a crash loop can't eat the CPU: 10 ms after a crash, doubling to at most 30 s, and back to 10 ms once the task has run 60 s since its last restart. The supervisor waits with recv's timeout, so a pending restart costs nothing. Each crash goes to telemetry as a crash event with the restart count and the backoff (crash-loop, backoff-reset). The agent asks it to stop a task (supervisor::OP_STOP: the kernel's stop, reported as death kind 5, never restarted) or to start a dead one again (OP_START, with its backoff reset), for deployments (15.4). Test features: give-up-after-3 and give-up-after-3000 stop restarting so a run made only of a crash loop can end, backoff-fast restarts at once, reset-after-2s shortens the reset window, and halt-on-exit stops the system when any task exits.

10Drivers#

Device drivers are ordinary tasks. The kernel discovers PCI devices at boot and a manifest grants one to a task (devices = ["virtio-console"]). The driver gets:

  • the device's register BARs mapped into its address space (uncached), except the BAR holding the MSI-X table: the kernel programs interrupt routing itself;
  • read-only access to the device's PCI configuration space;
  • a physically contiguous DMA region (dma_pages), the same physical pages for the life of the task slot and zeroed on every restart;
  • the device's interrupts as notifications in recv (sender 0, NOTIFY_IRQ). A driver with work in flight passes RECV_EXPECT_IRQ so the kernel idles for it instead of ending the run.

Drivers: virtio-console, virtio-vsock (one stream to host CID 2, port 5000), virtio-blk and virtio-net (14), all on the shared user/virtio crate (virtio 1.x modern PCI, split virtqueues). A crashing driver is restarted by the supervisor; it resets the device and carries on, and its clients see DEAD and retry against the new id (console-restart, blk-restart, nic-restart).

A driver that must tell its client something without being asked (frames arrived) posts a notification with notify(client, bits) rather than sending: only the client sends, so the two can't deadlock. The client gets the bits in recv as sender 0, NOTIFY_POST.

Limit

There is no IOMMU yet. A driver programs its device with physical addresses, so a malicious driver could make the device read or write any memory, kernel included. Driver tasks are isolated from mistakes (bad pointers, crashes, runaway loops), not from malice. Step 7 plans VT-d DMA remapping (plans/step-7-iommu.md).

11Telemetry#

The kernel logs events at its control points into a 128-entry ring: task start, exit, fault (vector, rip, cr2), CPU-budget kill, restart, refused IPC sends and rejected images. The task with events = true (user/telemetry) forwards them as newline-delimited JSON through the uplink driver, with a heartbeat every second, log lines from other tasks, storage events, and network events and counter snapshots (14.5).

{"seq":5,"t":1,"task":"crasher","id":"2","event":"fault","vector":14,"rip":"0x400182","cr2":"0x10"}
{"seq":6,"t":2,"task":"crasher","id":"2.1","event":"restart","previous":"2"}
{"t":2,"task":"supervisor","id":"1","event":"crash","of":"crasher","index":2,"kind":"fault","code":14,"restarts":1,"backoff_ms":20}
{"t":5,"event":"dropped","count":37}
{"t":102,"event":"heartbeat","n":1,"frames":89,"irqs":3,"events":11,"tasks":[...]}

t is in 10 ms ticks since boot; ids are slot or slot.generation. Kernel events carry seq; if the ring wraps before telemetry reads it, a dropped record says how many were lost. The uplink is the virtio console by default (QEMU writes it to build/telemetry.log), or vsock with TRANSPORT=vsock and an uplink task running virtio-vsock.

tools/host-agent.py build/telemetry.log            # console uplink
tools/host-agent.py --listen-vsock 5000 &          # vsock: listen first, then boot
make run TRANSPORT=vsock ACCEL=kvm APP=tests/apps/telemetry-vsock.toml

host-agent.py checks that every line is JSON with an event, that sequence gaps are covered by dropped, and heartbeat spacing; --check turns problems into the exit status and --expect EVENT=N requires counts. --set-interval MS sets the counter snapshot interval once the guest connects (vsock), and --expect-interval TICKS checks that snapshots then arrive that far apart.

12Boot chain and attestation#

With BOOT=uefi-secure every link checks the next before running it:

Task images ship as boot modules beside the kernel, each with a .sig file (VNRSIG01, program name, version and SHA-256 of the ELF, signed with Ed25519). The kernel refuses an image that is unsigned, changed, signed for another program, signed by another key, or older than the manifest's min_version. A refused task never runs; the supervisor and telemetry are told why. Images can be updated without rebuilding the kernel, as long as they are signed.

Measured boot (TPM=1, swtpm): the firmware measures the boot loader and Secure Boot state into PCRs 0–7. Before any task runs, the kernel extends PCR 12 with SHA-256 of the kernel file, of the app manifest, and of each task's signed statement (zeros for a refused image). tools/expected-pcrs.py computes PCR 12 from the build output alone.

Attestation: the attest task (tpm = true) holds an attestation key in the TPM (restricted ECDSA P-256 under the endorsement hierarchy). When the host sends attest <nonce> over the vsock uplink, control asks attest, which returns a TPM quote of PCRs 0, 4, 7, 12 and 13 (13: images loaded into slots since boot, 15.3). tools/verify-quote.py checks it is genuine TPM output, over this nonce, correctly signed, consistent with the reported PCRs and the kernel's measurement log, and equal to an approved reference.

make image BOOT=uefi-secure APP=tests/apps/attest.toml USER_FEATURES=control/one-shot
tools/host-agent.py --listen-vsock 5000 --save build/telemetry.log --attest &
make run BOOT=uefi-secure ACCEL=kvm TPM=1 TRANSPORT=vsock APP=tests/apps/attest.toml USER_FEATURES=control/one-shot
tools/verify-quote.py --record build/attest-reference.json \
    --expected-pcr12 $(tools/expected-pcrs.py --app tests/apps/attest.toml)   # known-good boot
tools/verify-quote.py --reference build/attest-reference.json                  # later boots
What this does not prove yet
  • Development keys. Secure Boot uses Debian's snakeoil keys, whose private key is public, and the image key is a local dev key in keys/.
  • Trust on first use. The attestation key isn't tied to the TPM's endorsement certificate yet, so the verifier trusts the key recorded with the reference.
  • Recorded firmware values. PCRs 0, 4 and 7 are compared with a recorded known-good boot, not computed independently; only PCR 12 is.
  • No IOMMU. A signed but malicious driver can still use DMA after measurement.

13Storage#

DISK=1 attaches build/disk.img (64 MiB, kept between runs) as a virtio block device. Three tasks share the work:

TaskProgramRole
blockdevvirtio-blkthe driver: reads and writes raw 4 KiB blocks; only disk may send to it
diskstoragegives every client its own encrypted volume
keys or attestunlocker, attesthands disk the master key, and services' volume keys (13.6)

Clients send disk block requests (vanir_user::block: read, write, flush, info) with block numbers relative to their volume. There is no file system: a volume is 256 numbered 4 KiB blocks (1 MiB). The volume is chosen by the client's manifest name, which the storage task gets from the kernel (task_name of the sender), so a client can neither name nor reach another task's volume. A task's first request creates its volume.

13.1On-disk format#

Block b of a volume is encrypted with the volume key, nonce = b ‖ counter, and associated data = volume name ‖ b ‖ counter. The counter goes up on every write, so a nonce is never reused. Ciphertext that was changed, moved to another block or volume, or paired with another counter fails to decrypt: the client gets INTEGRITY and telemetry an integrity_error. A block never written (counter 0) reads as zeros. A disk without the magic is formatted on first use, and so is a disk in an older format (VNRSTOR2), with a message saying so.

The header is sealed the same way, as block number 264−1, and holds the volume's kind, name and size, and its writer epoch and lease (RFD 3; recorded, not yet used). On a volume's first read or write after each unlock, disk opens the header and checks it against the table; if it doesn't open or doesn't match, every read and write of that volume gets INTEGRITY. Volumes are of two kinds: a fixed task's, and (from RFD 3) a service's. The kind is in the table, so a task and a service with the same name get different volumes, and in the key's salt (below), so their ciphertext never opens in each other's.

13.2Keys#

The storage task starts locked, answering LOCKED to every request for a task's volume until it has the master key, and to every request for a service's volume until it has that service's key (13.6). The master key comes from one of two places:

  • The key server (keys, user/unlocker): a test stand-in for a local key store, with the key compiled in. If disk may send to keys, it asks for the key when it starts. keys gives it only to the task named disk.
  • The host, after attestation (tests/apps/attest-storage.toml). The key lives on the host (keys/master.key, made by host-agent.py, never in the image).

13.3Key release#

A boot that measures differently (a changed kernel, manifest or task image) gets no key, and the sealed key is useless to anything but that boot's attest task. OP_UNLOCK is accepted only from tasks named keys or attest.

13.4Restarts and events#

The supervisor restarts disk and blockdev like any task. A restarted blockdev resets the device; disk sees DEAD, finds the new driver and resends, keeping its key (storage-blk-restart). A restarted disk starts locked and must get the key again: from keys it asks for it itself (storage-restart); clients see DEAD and resend.

If disk may send to telemetry, it reports:

{"t":6,"task":"disk","id":"3","event":"storage_locked"}
{"t":6,"task":"disk","id":"3","event":"storage_unlocked","by":"keys"}
{"t":7,"task":"disk","id":"3","event":"volume_created","volume":"client-a","start":2}
{"t":9,"task":"disk","id":"3","event":"integrity_error","volume":"client-a","block":0}

task comes from the kernel, so no other task can report storage events in disk's name.

make run DISK=1 DISK_RESET=1 APP=tests/apps/storage.toml   # fresh disk: two clients write and check
make run DISK=1 APP=tests/apps/storage.toml                # same disk: they find their data
make run DISK=1 DISK_CORRUPT=client-a:0 APP=...            # flip a byte of client-a's block 0 first

13.5Service volumes and writers#

A service image loaded into a slot (15) can declare a volume in its signed descriptor (volume = { blocks = 16 }, at most 65536). The kernel returns the size with the rest of the descriptor (task_listen), and disk gives an instance in a slot its service's volume, named after the service, whichever slot it runs in. An instance whose descriptor declares no volume gets NOT_ALLOWED. The version that makes the volume fixes its size; an instance that declares another size gets OUT_OF_RANGE and can't open it (RFD 3 leaves resizing to RFD 4).

A service volume has one writer (RFD 3, P1). Any instance of the service may read it; writes and flushes from any other get FENCED. The writer is named by an epoch, which the control plane assigns with each deployment and the agent hands to disk (block::OP_EPOCH: epoch, lease, writer). Only the task with loads = true may send it. disk records a higher epoch in the volume's header and flushes it before replying. The same epoch again is accepted only while there is no writer, or the writer is unchanged. Anything lower is refused, across reboots too, since the header is on the disk. The writer is a slot, kept in memory: a writer that crashes and is restarted in its slot stays the writer, and a restarted disk knows no writer until the agent names it again. The lease is recorded, not enforced (RFD 3, determination 8).

13.6Service keys#

Each service's volume has its own key (RFD 3, P2). The control plane makes it on first use, keeps it (build/cp-volume-keys/<service> for the mock), and sends it only to an attested node that runs the service. The agent forwards it but can't read it: the key is sealed to attest's per-boot X25519 key, which the handshake's quote binds along with the agent's own keys. The agent can dial out and load images, so a compromised agent shouldn't also be able to read every volume on the node.

  • Only for that service. The service name is the seal's associated data, so a blob moved to another service doesn't open (agent-volume-key-swap); the agent reports key-refused <service>.
  • Only to attested nodes. A node that said no-tpm gets no keys, so a service with a volume never gets ready there (agent-volume-unattested).
  • Without its key a service's volume answers LOCKED; task volumes and other services are unaffected, and so is OP_EPOCH for other services. The instance never says it is ready, and the deployment fails (volume-no-key).
  • Forgotten. Once a commit leaves no instance of a service on the node, the agent has disk forget its key and drops the blob (volume-forget). A node only holds the keys of what it runs.
  • The stand-in. keys serves a test key per service as well (HKDF of a fixed seed and the name), and disk asks it when it needs one, so the one-node tests run without a TPM or a control plane. An app with keys accepts either source; the attested app (agent-volumes-tpm.toml) has none.

OP_SERVICE_KEY is accepted only from keys and attest, OP_FORGET_KEY only from the task with loads = true. A volume written under V1's keys (salt vanir-service-v1, from the master key) no longer opens.

14Networking#

Services serve TCP from tasks of their own, as RFD 1 (rfd/0001-network-services.md) proposes. Each network has a NIC driver task and a network stack task, and the management and data networks are separate: a flood or a compromise of the data stack can't reach the stack the control plane uses. Everything is declared in the manifest; nothing here loads at run time.

14.1Drivers and stacks#

user/virtio-net moves Ethernet frames between a virtio-net device and one client, and knows nothing about IP (vanir_user::nic): OP_SEND_FRAME takes one frame, OP_RECV_FRAMES returns as many waiting frames as fit in 4 KiB and never waits, OP_INFO gives the MAC and the interface counters. It negotiates only VERSION_1 and MAC: no checksum offload, so smoltcp computes checksums. Sixteen 2 KiB receive buffers stay posted. The receive interrupt is on only after the client has emptied the ring; the driver then posts NOTIFY_RX to it with notify, turns the interrupt off, and the client polls until the ring is empty again (as Linux's NAPI does).

user/net runs smoltcp 0.12 (ARP, IPv4, TCP, DHCP) with no heap: 96 sockets with 4 KiB buffers each, in fixed arrays. Only net sends to the driver, and the driver only posts notifications back, so the two can't deadlock. The same program runs both stacks: the task named net drives nic, and mgmt-net drives nic-mgmt. Both use DHCP; the net/static-addr test feature gives the data stack 10.0.9.2/24 instead, for the dgram backend, which has no DHCP server.

net spends at most half of each tick on received frames. Past that, frames wait in the driver's ring until the next tick and the device drops what doesn't fit, so a flood can't take the CPU from the services or the management stack (mgmt-under-flood). The budget is measured with the TSC, so time net spends preempted counts too.

14.2Sockets#

A service declares its ports in the manifest (listen, 7). net asks the kernel which ports a client may use (task_listen), so a task can't claim ports it wasn't given (http-undeclared-port), and the build refuses two services declaring one port (build-http-port-clash). Instances of one service (service = "web") may share a port.

OpMessage → reply

Handles carry a generation, as task ids do, so a handle kept after its connection closed can't name a newer one. smoltcp has no accept queue (one socket holds one connection), so net keeps a few sockets listening on each port in use and hands each connected one to the live instance of the port's service.

user/http is a small HTTP/1.1 server on this interface: GET and HEAD, keep-alive, fixed buffers. / answers hello from <task> and /count the number of requests. When either side restarts, the other recovers: HTTP finds net again and listens anew (net-restart), and net forgets a restarted instance's connections (http-restart).

14.3Routing and draining#

Each service has one live instance, which gets its new connections; existing connections stay where they are. An instance becomes live only after it has said OP_READY. The first ready instance of a service becomes live by itself; after that, a task with routes = true changes it with OP_ROUTE (route-not-ready, route-not-allowed). In the RFD 1 tests that task is switcher; RFD 2's agent does it too (15.4), and asks an instance's status with OP_STATUS (starting, ready, live, draining, drained) instead of waiting for a drain's reply (DRAIN_NOWAIT).

Connections the draining instance never accepted go to the live instance. HTTP leaves idle connections alone while draining: closing one just as its client sends a request would fail that request. With eight clients requesting without pause, no request fails and every client ends up on web-2 (swap-under-load); a connection held open without a request is reset at the deadline and counted (drain-deadline).

14.4Limits#

Before smoltcp sees a frame, net checks it:

  • sources on the blocklist are dropped first (16 ranges with expiry, set by OP_BLOCK from a task with routes = true);
  • IPv4 packets with a bad header checksum are dropped and counted;
  • each new connection (a SYN for one of our ports) is held to the port's max_per_source and max_connections, and to 16 handshakes in progress per port. smoltcp has no SYN cookies, so at that cap a new SYN takes the place of the oldest handshake; handshakes also time out after 2 s.

HTTP limits each request: the header must fit in 4 KiB (else 431) and arrive within 5 s of its first byte (else 408), and bodies over 16 KiB are refused (413). Connections idle for 15 s between requests are closed by HTTP, and for 60 s by net. A 32-entry Space-Saving sketch tracks the heaviest sources; each snapshot interval net compares SYN and limit-drop rates and CPU budget use with fixed thresholds and reports attack_suspected with the top talkers.

Not yet tested

The attack tests planned in plans/step-9-net.md (dos-*: SYN flood, connection exhaustion, slowloris, large requests, packet flood, blocklist) are not in the suite yet. The packet flood is covered by mgmt-under-flood; the other limits are implemented but not exercised by a test.

15Deployment#

Services are deployed while a node runs, and move between nodes (RFD 2, rfd/0002-deployment.md; the plan is plans/step-10-deploy.md). A node's manifest can't name every service that might land on it, so it declares a pool of generic slots. The agent (user/agent, the only task with loads = true) loads signed service images into them at run time. Until there is a control plane, test scripts built into the agent stand in for it.

15.1Slots and descriptors#

[[slot_class]]
name = "small"           # slots are named small-0, small-1, ... after the tasks
count = 2
memory_pages = 256       # most frames a service may use: image, stack, page tables
image_pages = 128        # image area: the largest image a slot can hold (512 KiB)
budget = 20              # optional: CPU budget, as for tasks
sends = ["net"]          # optional: tasks its services may send to (by task name)

Each slot is a task table entry that starts empty. At boot the kernel sets aside its image area (contiguous, never freed, like a DMA region) and checks that free memory covers every slot at its class's limit. Tasks' memory is fixed once loaded (there is no syscall to grow it), so after that check a load can't fail for want of memory. The manifest decides the table's size: tasks plus slots, at most 64.

What a service may do comes with its image, in a descriptor signed with it (tests/slots/*.toml):

name = "web"             # the service
version = 2
min_version = 1          # oldest version that may still run
slot_class = "small"
listen = [{ port = 80, max_connections = 64 }]
drain = { default_secs = 30, max_secs = 300 }
volume = { blocks = 256 }  # optional: the service's volume (RFD 3, 13.5)

tools/sign-image.py sign-slot KEY ELF DESC.toml OUT compiles it to the fixed 256-byte layout the kernel reads (OUT.desc) and writes a VNRSIG02 signature file (OUT.sig, 176 bytes) over the name, version, and SHA-256 of both the image and the descriptor, with the boot images' key. The Makefile builds the test images (SLOT_IMAGES) into build/slots/, then the agent, which carries them. task_listen answers for a slot from its descriptor, so net lets a service listen only on the ports it was signed with; it also returns the version, and http in a slot calls itself e.g. web v1 on small-0.

15.2Loading an image#

The agent copies the image into an empty slot's image area in pieces (slot_stage, so it never needs a buffer the image's size), then calls slot_load with the signature file and descriptor. The kernel, in order:

  1. checks the signature, and that it covers this image and this descriptor;
  2. checks the version against the descriptor's min_version;
  3. checks the descriptor names the slot's class;
  4. builds the address space, and refuses if it needs more frames than the class allows;
  5. measures it (below), or fails with BUSY or LOG_FULL having changed nothing;
  6. records the descriptor and starts it as a new generation of the slot.

A refused image fails with REJECTED and the reason, is logged as an image_rejected event, and is wiped from the image area. A crashed service is restarted from the image area like any task (9), without being measured again. slot_unload empties a slot whose service has ended: it zeroes the image area and measures the unload. A slot holding an image, running or not, can't be staged over.

15.3Measuring what runs#

Each load and unload is extended into PCR 13 and recorded in the kernel's run-time log: 80-byte entries (operation, slot, service name, version, SHA-256 of the signed statement), and PCR 13 is extended with each entry's SHA-256. The kernel keeps the log, as it does the boot log, so a crash of any task can't make the node unattestable. It has a fixed length (runtime_log in the manifest, default 1024 entries, about 80 KiB); when it is full, loads fail with LOG_FULL until the node reboots.

The attestation task sends TPM commands itself, so it takes a lock the kernel holds (tpm_lock/tpm_unlock) around each sequence of commands, and the kernel extends PCR 13 only while nobody holds it: a load meets BUSY instead of waiting. The kernel drops the lock if the task dies. Quotes cover PCRs 0, 4, 7, 12 and 13 and say how many run-time entries they cover; control then forwards those entries (attest::OP_RUNTIME_LOG, a JSON line of up to 20 at a time), and tools/verify-quote.py replays them to PCR 13 and lists what was loaded. tools/expected-pcrs.py --runtime load:small-0:web-v1 ... computes PCR 13 from the build. RFD 8 lists what this leaves open (rollback through an old descriptor, one key for boot and slot images, a task that holds the TPM lock forever).

15.4The lifecycle and the local swap#

The agent owns every slot's state (RFD 2, P4) and reports each transition as an instance event (slot, service, version, from, to) to telemetry:

A local swap deploys a new version of a service into an empty slot while the old one serves: the agent loads it, waits until net says it is ready (net::OP_STATUS), makes it live (OP_ROUTE), and drains the old instance without waiting on net (OP_DRAIN with DRAIN_NOWAIT, then OP_STATUS until it is drained). The drain deadline is the descriptor's default, or what the deployment asks for capped at the descriptor's maximum. Once drained, the agent asks the supervisor to stop it (supervisor::OP_STOP): the kernel ends it (stop, death kind 5) and the supervisor never restarts a stopped task. Its slot keeps the image, so a rollback is the same flow with the roles reversed: the supervisor starts the stopped slot again (OP_START, backoff reset) and the newer version drains. Commit unloads the stopped slots of a service. A service that exits 0 by itself is done and isn't restarted. Nothing in the lifecycle blocks: each deployment advances a step at a time from the agent's loop. For a service with a volume, a deployment carries a writer epoch, which the agent hands to disk before routing to the new instance if there is no old one, and otherwise once the old one has drained and before it is stopped (13.5). If disk refuses it, the new instance stays live without it, and the agent reports the refusal.

Tests: deploy-under-load and rollback-under-load keep eight clients requesting through the swap (and back) with no failed request; deploy-not-ready leaves the old version live when the new one never says it is ready; drain-deadline-cap, deploy-commit, slot-exit-clean.

15.5The agent and the control plane#

The agent dials the control plane through the management stack (mgmt-net; it has connects = true, and net::OP_CONNECT opens the connection), at the address built in (CP_ADDR, by default 10.0.2.2:7000: the host, through slirp). It reconnects with backoff (100 ms doubling to 10 s) whenever the connection drops; deployments go on meanwhile (user/agent/src/control.rs).

  • Who it talks to. The control plane's Noise static key is pinned in the agent at build time (keys/cp-noise.pub), so the agent talks to no one else (agent-wrong-cp-key). The agent's own static and ephemeral keys are fresh for each connection (RDRAND).
  • Who the node is. The first handshake message carries a TPM quote from attest (OP_QUOTE_FOR) over SHA-256(ephemeral key || static key || seal_pub), where seal_pub is attest's own per-boot key that service keys are sealed to (13.6): the keys of this handshake belong to a measured boot of a known image, and the private keys never leave the agent. The control plane checks it (agent-attested) and refuses a quote that binds another key (agent-unbound-key). A node without a TPM says no-tpm; --require-attestation refuses it.
  • What it wants. Desired state is a text document signed with a second pinned key (keys/cp-sign.pub), with a generation the agent only lets rise, so a replayed or reordered command does nothing (agent-signed-state). Lines: live <service> <slot> <image hash> [drain <s>] [epoch <n> <lease ms>], stop <service> [drain <s>], commit <service> (and end, for tests). Images are named by the SHA-256 of their signed statement. For a service with a volume, epoch names its writer (13.5): the agent gives it to the new instance in a deployment, or to the live instance if only the epoch changed. The mock control plane raises it whenever the live instance changes.
  • Reconciliation. The agent keeps moving towards the last state it applied: fetching an image it lacks straight into the named slot, deploying it, rolling back to a stopped slot that already holds the wanted image, draining, committing. It reports what it has after the handshake, on every change and every 5 s, so a dropped connection costs nothing but time (agent-reconnect, agent-deploy, agent-drain). A slot whose instance holds its volume's epoch reports epoch <n>, and epoch-refused <n> while disk refuses the one asked for (agent-epoch-stale). In agent-volume, four clients keep counting through a deployment of counter, and no count is answered twice.
  • Telemetry goes to the control plane through the agent. With no uplink driver, the telemetry task keeps its lines in a 16 KiB ring and the agent pulls them (telemetry::OP_PULL): if telemetry pushed to the agent while the agent sends to net and net to telemetry, the three could deadlock.

The Noise code (user/noise, no heap) and the host's (tools/vanir_noise.py, written separately from the spec) are both checked against the cacophony test vector in tests/vectors/noise-ik.json (noise-vectors, a host check). tools/control-plane.py gen-keys keys makes the dev keys on the first build; tests run it with CP=<scenario> (20).

15.6Moves, evacuation and updates#

A move takes a service to another node with the same pieces as a swap, driven by the control plane: it makes the service live on the new node, sends new connections there (its load balancer), then drains and stops the old instance and commits. Clients of the old node get Connection: close on their next request and reconnect through the load balancer to the new one (move-under-load: eight clients, no failed request).

A node's own image (kernel, drivers, net, the agent) only changes when it runs no instances (RFD 2, determination 1). The desired-state line update is refused by a node with instances, and its report says how many (agent-update-refused). The control plane evacuates it first, moving each instance away; an empty node then asks the supervisor to reboot it (supervisor::OP_REBOOT, the kernel's reboot: the 8042 reset line), and comes back with the image installed now. Its reports carry the node's name and its own signed version, so the control plane sees which image it rejoined with (evacuate-update: node a refuses, is evacuated to node b, reboots into an image signed as version 2, rejoins, and the service moves back, all under load).

tests/two-nodes.sh runs these cases: two images from one tree (agent built with NODE=a or b; with UPDATE=1 a second one for node a with SIGN_VERSION=2), two QEMUs (data ports 8080 and 8090), the control plane with its load balancer on port 8000, and the peer through it. QEMU runs with -no-reboot, so a reboot ends it with status 0, and the harness boots node a again from the updated image, standing in for an A/B update of its disk. Staging that image on a real disk is out of scope (RFD 2's plan).

18Limitations#

Stated plainly, in one place:

  • No IOMMU. Driver tasks can point their devices at any memory, including the storage task's key. Planned for step 7.
  • No KPTI. The kernel and the physical-memory map are mapped (supervisor-only) into every task. On Meltdown-affected CPUs (such as the development host's i7-7500U) user code could read them.
  • The hypervisor sees everything. Keys and plain text are in guest memory, which the host can read. Protecting against the host needs AMD SEV-SNP or Intel TDX.
  • Development keys and trust on first use in the boot chain (12).
  • No storage rollback protection. An older data block written back with its older counter and tag still decrypts. Fixing it needs a root of freshness, e.g. a Merkle root in TPM NV storage.
  • Plain-text volume table. Task names, volume positions and which blocks were ever written are visible; editing the table is a denial of service.
  • Storage isn't crash-consistent. Data is written before its metadata; a crash in between leaves that block failing its integrity check until rewritten. Nothing is guaranteed durable before a flush.
  • Volumes are never freed, and a fixed task's volume is always 256 blocks. A service's volume is sized by its descriptor, and that size can't change.
  • Writes are refused during a handoff of a service with a volume, from the routing change until the old instance has drained (RFD 3, V3 makes them wait). Writer leases are recorded, not enforced.
  • The control plane holds every service's key (RFD 8, vector 7), in plain files for the mock (build/cp-volume-keys/). Keys are never rotated.
  • One key release per boot. In the attested flow the host says bye after releasing the key, so a disk restarted later stays locked until the next boot.
  • One CPU, no IPC priorities, messages copied (no memory lending). Network bytes are copied twice through IPC.
  • Network limits without attack tests. The connection caps, half-open cap and blocklist in net are implemented but the planned dos-* tests aren't written yet (14.4).
  • TCP over IPv4 only, no TLS, no SYN cookies (smoltcp has none), 10 ms TCP timer resolution, and no retransmit counter.
  • Restarting is the only crash policy. A service that crashes on every request is restarted forever, at most every 30 s; rolling back or blocking the client that triggers it is RFD 7.
  • Known gaps in deployment (RFD 8): the version floor is each image's own descriptor, so the control plane or a compromised agent can load an old release with its old descriptor; boot and slot images are signed with one key, so a signature doesn't say which kind of image it is for; attest keeps its raw TPM mapping, so a compromised attest can hold the TPM lock forever and block every load; anything that can trigger loads can fill the run-time log, after which the node refuses loads until it reboots; a service that can be made to exit 0 stays down; the control plane's keys are in the image, so rotating them means updating every node.
  • A mock control plane. tools/control-plane.py stands in for the real one (scheduling, load balancers, the fleet view are a later RFD). Nodes are named by a name built into the agent (NODE), not by their TPM's key, and the two-node tests boot an updated node from a new ISO rather than writing it to an A/B boot disk.
  • Fixed slot classes, stateless services. Slots come in classes fixed by the manifest (sizing them per service is RFD 4).

23.1Add a user program#

  3. Add "user/<name>" to members in the root Cargo.toml and <name> to USER_PROGS in the Makefile (that also makes it a boot module and signs it).
  4. Reference it from a manifest: program = "<name>".

23.2Add a test case#

  1. Add a manifest in tests/apps/ if no existing one fits.
  2. Put test-only behaviour behind a cargo feature in the program's Cargo.toml, with a comment saying what it tests.
  3. Add a row to CASES in tests/run.sh, after the cases whose state it depends on.
  4. Run it alone (ONLY='^name$' make test), then break the protection on purpose and confirm the case fails, then restore and run both full suites.
  5. Add it to 21 and, for a protection, 17.

23.3Add a syscall#

  1. Pick an unused number; add SYS_<NAME> to kernel/src/syscall.rs and a dispatch arm.
  2. Implement the handler (in kernel/src/process.rs if it touches the task table). Read arguments from the TrapFrame; write results to rax/rdx/rsi. Validate every user pointer with the address space's check_range and copy through usercopy. Never block inside the handler: mark the task blocked and switch.
  3. Add the same constant and a wrapper to user/lib/src/lib.rs.
  4. Restrict privileged calls to the right task (as restart is supervisor-only) and return NOT_ALLOWED otherwise.
  5. Document it in 16.

23.4Add a kernel or storage event#

  1. Kernel event: a constant in kernel/src/events.rs (document what a, b, c hold), events::log(...) at the control point, the same constant in user/lib events, and a format arm in event_line in user/telemetry.
  2. Storage event: a kind constant in user/lib telemetry, a format arm in storage_line, and self.event(kind, block, name) in user/storage.
  3. Check it with tools/host-agent.py - --quiet --check --expect <event>=1 in a cmd: test.

23.5Add a device kind or driver#

  1. Add (name, vendor, &[device ids]) to KINDS in kernel/src/pci_kinds.rs (shared with build.rs, which validates manifests).
  2. Add the QEMU device to QEMU_FLAGS (behind a variable, as DISK is) with disable-legacy=on for virtio.
  3. Write the driver on user/virtio; take requests by IPC; handle NOTIFY_IRQ; use RECV_EXPECT_IRQ while work is in flight.
  4. Add a crash feature and a restart test, as virtio-blk/crash-after-10.

23.6Add a manifest key#

  1. Add it to known in kernel/build.rs, parse and validate it, and emit it in the generated Task literal.
  2. Add the field to Task in kernel/src/process.rs.
  3. Document it in apps/README.md and 7.

24Invariants#

Rules the code relies on. Breaking one is a bug even when the tests pass.

  1. Every commit passes the full suite under both TCG and KVM.
  2. Stable Rust only. No nightly features or -Z flags.
  3. The kernel never blocks mid-syscall. Waiting means saving registers, marking the task blocked, and writing results into its saved frame later.
  4. User pointers are untrusted. Range-checked and copied with fault recovery under SMAP; never dereferenced directly.
  5. Identity comes from the kernel. Servers decide who a client is with task_name(sender), never from message contents.
  6. W^X everywhere. No mapping is both writable and executable.
  7. Mechanism in the kernel, policy in tasks. Restart decisions belong to the supervisor; key decisions to keys/attest/the host.
  8. Default deny. No IPC without sends; no device without a grant; storage locked until keyed.
  9. Secrets stay out of git and out of images. keys/ is ignored; the storage master key is never on the disk.
  10. Crypto uses the portable backends. The --cfg flags in .cargo/config.toml select them; removing them makes rustc crash (SIGILL) on this target.
  11. The measured set is the source of truth. Kernel, manifest and task statements go into PCR 12; tools/expected-pcrs.py must compute the same value.
