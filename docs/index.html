Reference manual · x86-64 · stable Rust · Limine

A minimal x86-64 kernel that runs isolated, unprivileged tasks which talk only by messages. Drivers, storage and attestation are ordinary tasks, and the system is fixed at build time.

How to read this

Part one explains each layer from scratch, for readers who haven't built an operating system before. Part two is the reference: what each subsystem does, its interfaces, and the tests that prove it. Part three is for working on the code, by people or by coding agents: commands, file locations, recipes, rules and fixes. Agents should start at 17. Agent quick reference or fetch llms.txt.

Part one: guide

1Introduction#

vanir-os is a small kernel written in stable Rust and booted by Limine. Its design follows Oxide's Hubris: a fixed set of tasks is declared at build time, each runs in its own address space in ring 3, and they cooperate through synchronous send/receive/reply messages. Things a larger kernel does internally, such as device drivers, restarting failed programs, storage and talking to a host, are separate tasks here.

The kernel provides:

  • serial output, GDT/TSS, IDT, and an ELF loader that enforces W^X
  • a page-table tree per process, with SMEP, SMAP and NX
  • a 100 Hz local APIC timer, round-robin preemption and CPU budgets
  • synchronous IPC with a per-task allowlist of who may send to whom
  • supervisor notifications and task restarts with generation-checked ids
  • PCI device grants, MSI-X interrupts and DMA regions for driver tasks
  • a kernel event log, signature checks on task images, and boot measurements into a TPM

On top of that, as tasks: virtio console, vsock and block drivers; telemetry streamed to a host agent; TPM remote attestation; and encrypted per-task storage whose key the host releases only to a boot it has attested.

Static

No fork or exec. The manifest fixes every task, its budget and who it may talk to.

Isolated

Each task has its own page tables. A crash ends that task, not the system.

Mechanism, not policy

The kernel reports deaths; the supervisor task decides what to do.

Verifiable

Signed images, Secure Boot, measured boot and TPM quotes, all checked by tests.

3The layers, from scratch#

An operating system is a stack of layers, each depending on the one below. This part walks up the stack once, saying in plain terms what each layer is for and how vanir-os does it. The reference in part two goes into detail.

3.1The machine#

In plain terms

A computer is a processor that runs instructions from memory, plus devices (disk, network, serial port) it talks to through special addresses. When it powers on, it runs firmware burned into the board, which finds a boot loader on a disk, which loads the kernel into memory and jumps to it. From then on the kernel is in charge.

vanir-os runs in QEMU, which emulates the machine in software (TCG) or uses the host CPU's virtualization (KVM). The firmware is SeaBIOS or OVMF; the boot loader is Limine, which also loads every task's ELF file and signature as "modules" next to the kernel.

3.2Privilege#

In plain terms

x86 processors have privilege levels called rings. Code in ring 0 can do anything: change memory maps, talk to hardware, turn off interrupts. Code in ring 3 can't, and if it tries, the processor stops it and hands control to ring 0. The kernel runs in ring 0; programs run in ring 3. That's what keeps a buggy or hostile program from taking over the machine.

The kernel sets this up with a GDT (segment descriptors for each ring), a TSS (which stack to switch to when ring 3 traps into ring 0), and CPU features: SMEP stops the kernel running user code, SMAP stops it reading or writing user memory except inside explicit copy routines, NX marks data pages non-executable, and CR0.WP makes read-only pages read-only for the kernel too.

3.3Virtual memory#

In plain terms

Programs don't see physical memory directly. Every address they use goes through page tables, a tree the processor walks to translate a virtual address to a physical one, 4 KiB at a time. Each page also has permissions: present, writable, user-visible, executable. Give each program its own page tables and it can't even name another program's memory.

3.4Traps: syscalls, faults, interrupts#

In plain terms

There are three ways into the kernel. A syscall is a program asking for something on purpose (here, with the int 0x80 instruction). A fault is the processor reporting a mistake, such as touching unmapped memory. An interrupt is a device or timer asking for attention. All three save where the program was, switch to ring 0, and run a handler listed in the IDT.

The timer interrupt fires 100 times a second. It's how the kernel takes the CPU back from a task that never gives it up (preemption) and how it counts CPU budgets.

3.5Tasks and messages#

In plain terms

A task (or process) is a program with its own memory and saved registers. The kernel switches between them quickly so they seem to run at once. Isolated tasks still need to cooperate, so they send each other messages: a client sends a request and waits; the server receives it, does the work and replies. The kernel copies the bytes between their memories and checks who is allowed to talk to whom.

vanir-os declares every task in an app manifest. The kernel never creates tasks at run time; it can only restart one, when the supervisor task asks.

3.6Devices#

In plain terms

Software controls a device by writing to its registers, which appear as memory addresses (MMIO). Fast devices also read and write main memory themselves: DMA, direct memory access. When they finish, they raise an interrupt. A driver is the code that knows a device's registers and protocol.

Here a driver is an ordinary ring-3 task. The kernel maps only that device's registers into the driver, gives it a fixed DMA region, and turns the device's interrupts into messages. A crashing driver is just a crashing task.

3.7Trust: signatures, measurements, keys#

In plain terms

Isolation protects tasks from each other, but how do you know the right code is running at all? Each boot stage checks a signature on the next before running it. Each stage also measures (hashes) what it runs into a TPM, a small security chip that keeps a running hash it can't be made to forget. Later the TPM can sign a quote of those hashes, so a remote host can verify what booted. Only then does the host hand over secrets, such as the key that decrypts the disk.

5Memory and address spaces#

Physical memory is handed out in 4 KiB frames from Limine's memory map, with a free list so frames return when a task dies. The kernel reaches physical memory through the HHDM (Limine's direct map). Each task gets its own PML4; the kernel half is shared and supervisor-only.

Two software bits in page-table entries record ownership: DEVICE (bit 9, MMIO, never freed) and PINNED (bit 10, DMA frames owned by the task slot, kept across restarts). Everything else a task maps is freed when it dies; the no-leak and restart-no-leak tests check the frame count returns to its baseline.

The kernel touches user memory only through copy_from_user and friends, which open a SMAP window (stac/clac) and recover from page faults through an exception table, so a bad pointer in a syscall returns an error instead of crashing the kernel.

6Tasks and scheduling#

  • Static task table. The tasks are fixed at build time by an app manifest (7). Tasks get ids 1, 2, … in manifest order.
  • One kernel stack. A trap saves the user's registers on it. A context switch stores that frame in the current task, copies the next task's saved frame over it, switches CR3, and returns through the normal iretq. Kernel code never waits in the middle of a syscall: a task that must wait is marked blocked with its registers saved, and whoever completes the operation writes the results into those saved registers.
  • Round-robin preemption on the 100 Hz timer. A task with a budget is killed after that many ticks of CPU.
  • Outcomes. A task ends by exit, by faulting, or by using up its budget; the others keep running. When nothing can run, the kernel prints a summary and halts with a status (18). Tasks waiting in recv count as idle servers; tasks stuck in send mean a deadlock.

7App manifests#

An app manifest is a TOML file listing every task. kernel/build.rs turns it into the kernel's task table at build time. Pick one with make run APP=… (default apps/default.toml; tests use tests/apps/).

[[task]]
name = "client"        # unique task name; also the program, unless `program` is set
program = "hello"      # optional: build/<program>.elf (any program under user/)
budget = 50            # optional: CPU budget in 10 ms ticks (default: unlimited)
supervisor = true      # optional: told when other tasks die (at most one)
sends = ["echo"]       # optional: tasks this one may send IPC messages to
devices = ["virtio-console"]  # optional: PCI devices to drive (kernel/src/pci_kinds.rs)
dma_pages = 16         # optional: contiguous DMA region in 4 KiB pages (max 256)
events = true          # optional: may read the kernel event log and stats (at most one)
min_version = 2        # optional: refuse images signed with an older version
tpm = true             # optional: gets the TPM mapped, for attestation (at most one)

The build fails on unknown keys, duplicate names, unknown sends targets or device names, or more than one supervisor, event reader or TPM task. Each devices entry claims the next unclaimed device of that kind; a missing device is logged and the task runs without it.

8IPC#

Synchronous send/receive/reply, as in Hubris. A client's send waits until the server has received the message and replied. The kernel copies messages and replies between address spaces, up to 4 KiB each. A task may only send to the tasks listed in its manifest sends.

Task ids carry a generation (slot + 1 | generation << 16) that changes on restart. A client holding an id from before a restart gets DEAD instead of silently reaching a fresh server that lost its state; it can lookup the name again and resend. Kernel notifications arrive as messages from sender 0.

Error (top bit set)Meaning
DEADthe target has died, or was restarted since the id was obtained
NOT_ALLOWEDthe target is not in the sender's sends (or: supervisor-only call)
BAD_TARGETno such task, or sending to yourself
BAD_BUFFERa buffer is unmapped, read-only where it must be written, or not in user memory
TOO_LONGa message or reply is over 4 KiB or bigger than the receiving buffer
BAD_ARGUMENTa reply code with the top bit set; restart of a live or already-restarted task

9Supervisor#

One task may be marked supervisor = true (user/supervisor). The kernel reports every other task's death to it as a message from sender 0 with NOTIFY_DEATH and a death record: how it ended, exit code or fault vector, rip, cr2, error code and ticks used. The supervisor decides what to do and may call restart(id), which reloads the task's ELF into fresh memory with a new generation. The policy lives in the supervisor, not the kernel. If the supervisor itself dies, the kernel halts.

10Drivers#

Device drivers are ordinary tasks. The kernel discovers PCI devices at boot and a manifest grants one to a task (devices = ["virtio-console"]). The driver gets:

  • the device's register BARs mapped into its address space (uncached), except the BAR holding the MSI-X table: the kernel programs interrupt routing itself;
  • read-only access to the device's PCI configuration space;
  • a physically contiguous DMA region (dma_pages), the same physical pages for the life of the task slot and zeroed on every restart;
  • the device's interrupts as notifications in recv (sender 0, NOTIFY_IRQ). A driver with work in flight passes RECV_EXPECT_IRQ so the kernel idles for it instead of ending the run.

Drivers: virtio-console, virtio-vsock (one stream to host CID 2, port 5000) and virtio-blk, all on the shared user/virtio crate (virtio 1.x modern PCI, split virtqueues). A crashing driver is restarted by the supervisor; it resets the device and carries on, and its clients see DEAD and retry against the new id (console-restart, blk-restart).

Limit

There is no IOMMU yet. A driver programs its device with physical addresses, so a malicious driver could make the device read or write any memory, kernel included. Driver tasks are isolated from mistakes (bad pointers, crashes, runaway loops), not from malice. Step 7 plans VT-d DMA remapping (plans/step-7-iommu.md).

11Telemetry#

The kernel logs events at its control points into a 128-entry ring: task start, exit, fault (vector, rip, cr2), CPU-budget kill, restart, refused IPC sends and rejected images. The task with events = true (user/telemetry) forwards them as newline-delimited JSON through the uplink driver, with a heartbeat every second, log lines from other tasks, and storage events.

{"seq":5,"t":1,"task":"crasher","id":"2","event":"fault","vector":14,"rip":"0x400182","cr2":"0x10"}
{"seq":6,"t":2,"task":"crasher","id":"2.1","event":"restart","previous":"2"}
{"t":3,"event":"log","from":"supervisor","msg":"giving up on task 2 after 3 restarts"}
{"t":5,"event":"dropped","count":37}
{"t":102,"event":"heartbeat","n":1,"frames":89,"irqs":3,"events":11,"tasks":[...]}

t is in 10 ms ticks since boot; ids are slot or slot.generation. Kernel events carry seq; if the ring wraps before telemetry reads it, a dropped record says how many were lost. The uplink is the virtio console by default (QEMU writes it to build/telemetry.log), or vsock with TRANSPORT=vsock and an uplink task running virtio-vsock.

tools/host-agent.py build/telemetry.log            # console uplink
tools/host-agent.py --listen-vsock 5000 &          # vsock: listen first, then boot
make run TRANSPORT=vsock ACCEL=kvm APP=tests/apps/telemetry-vsock.toml

host-agent.py checks that every line is JSON with an event, that sequence gaps are covered by dropped, and heartbeat spacing; --check turns problems into the exit status and --expect EVENT=N requires counts.

12Boot chain and attestation#

With BOOT=uefi-secure every link checks the next before running it:

Task images ship as boot modules beside the kernel, each with a .sig file (VNRSIG01, program name, version and SHA-256 of the ELF, signed with Ed25519). The kernel refuses an image that is unsigned, changed, signed for another program, signed by another key, or older than the manifest's min_version. A refused task never runs; the supervisor and telemetry are told why. Images can be updated without rebuilding the kernel, as long as they are signed.

Measured boot (TPM=1, swtpm): the firmware measures the boot loader and Secure Boot state into PCRs 0–7. Before any task runs, the kernel extends PCR 12 with SHA-256 of the kernel file, of the app manifest, and of each task's signed statement (zeros for a refused image). tools/expected-pcrs.py computes PCR 12 from the build output alone.

Attestation: the attest task (tpm = true) holds an attestation key in the TPM (restricted ECDSA P-256 under the endorsement hierarchy). When the host sends attest <nonce> over the vsock uplink, control asks attest, which returns a TPM quote of PCRs 0, 4, 7 and 12. tools/verify-quote.py checks it is genuine TPM output, over this nonce, correctly signed, consistent with the reported PCRs and the kernel's measurement log, and equal to an approved reference.

make image BOOT=uefi-secure APP=tests/apps/attest.toml USER_FEATURES=control/one-shot
tools/host-agent.py --listen-vsock 5000 --save build/telemetry.log --attest &
make run BOOT=uefi-secure ACCEL=kvm TPM=1 TRANSPORT=vsock APP=tests/apps/attest.toml USER_FEATURES=control/one-shot
tools/verify-quote.py --record build/attest-reference.json \
    --expected-pcr12 $(tools/expected-pcrs.py --app tests/apps/attest.toml)   # known-good boot
tools/verify-quote.py --reference build/attest-reference.json                  # later boots
What this does not prove yet
  • Development keys. Secure Boot uses Debian's snakeoil keys, whose private key is public, and the image key is a local dev key in keys/.
  • Trust on first use. The attestation key isn't tied to the TPM's endorsement certificate yet, so the verifier trusts the key recorded with the reference.
  • Recorded firmware values. PCRs 0, 4 and 7 are compared with a recorded known-good boot, not computed independently; only PCR 12 is.
  • No IOMMU. A signed but malicious driver can still use DMA after measurement.

13Storage#

DISK=1 attaches build/disk.img (64 MiB, kept between runs) as a virtio block device. Three tasks share the work:

TaskProgramRole
blockdevvirtio-blkthe driver: reads and writes raw 4 KiB blocks; only disk may send to it
diskstoragegives every client its own encrypted volume
keys or attestunlocker, attesthands disk the master key

Clients send disk block requests (vanir_user::block: read, write, flush, info) with block numbers relative to their volume. There is no file system: a volume is 256 numbered 4 KiB blocks (1 MiB). The volume is chosen by the client's manifest name, which the storage task gets from the kernel (task_name of the sender), so a client can neither name nor reach another task's volume. A task's first request creates its volume.

13.1On-disk format#

Block b of a volume is encrypted with the volume key, nonce = b ‖ counter, and associated data = volume name ‖ b ‖ counter. The counter goes up on every write, so a nonce is never reused. Ciphertext that was changed, moved to another block or volume, or paired with another counter fails to decrypt: the client gets INTEGRITY and telemetry an integrity_error. A block never written (counter 0) reads as zeros. A disk without the magic is formatted on first use.

13.2Keys#

The storage task starts locked, answering LOCKED to every request until it has the master key. It gets it from one of two places:

  • The key server (keys, user/unlocker): a test stand-in for a local key store, with the key compiled in. If disk may send to keys, it asks for the key when it starts. keys gives it only to the task named disk.
  • The host, after attestation (tests/apps/attest-storage.toml). The key lives on the host (keys/master.key, made by host-agent.py, never in the image).

13.3Key release#

A boot that measures differently (a changed kernel, manifest or task image) gets no key, and the sealed key is useless to anything but that boot's attest task. OP_UNLOCK is accepted only from tasks named keys or attest.

13.4Restarts and events#

The supervisor restarts disk and blockdev like any task. A restarted blockdev resets the device; disk sees DEAD, finds the new driver and resends, keeping its key (storage-blk-restart). A restarted disk starts locked and must get the key again: from keys it asks for it itself (storage-restart); clients see DEAD and resend.

If disk may send to telemetry, it reports:

{"t":6,"task":"disk","id":"3","event":"storage_locked"}
{"t":6,"task":"disk","id":"3","event":"storage_unlocked","by":"keys"}
{"t":7,"task":"disk","id":"3","event":"volume_created","volume":"client-a","start":2}
{"t":9,"task":"disk","id":"3","event":"integrity_error","volume":"client-a","block":0}

task comes from the kernel, so no other task can report storage events in disk's name.

make run DISK=1 DISK_RESET=1 APP=tests/apps/storage.toml   # fresh disk: two clients write and check
make run DISK=1 APP=tests/apps/storage.toml                # same disk: they find their data
make run DISK=1 DISK_CORRUPT=client-a:0 APP=...            # flip a byte of client-a's block 0 first

16Limitations#

Stated plainly, in one place:

  • No IOMMU. Driver tasks can point their devices at any memory, including the storage task's key. Planned for step 7.
  • No KPTI. The kernel and the physical-memory map are mapped (supervisor-only) into every task. On Meltdown-affected CPUs (such as the development host's i7-7500U) user code could read them.
  • The hypervisor sees everything. Keys and plain text are in guest memory, which the host can read. Protecting against the host needs AMD SEV-SNP or Intel TDX.
  • Development keys and trust on first use in the boot chain (12).
  • No storage rollback protection. An older data block written back with its older counter and tag still decrypts. Fixing it needs a root of freshness, e.g. a Merkle root in TPM NV storage.
  • Plain-text volume table. Task names, volume positions and which blocks were ever written are visible; editing the table is a denial of service.
  • Storage isn't crash-consistent. Data is written before its metadata; a crash in between leaves that block failing its integrity check until rewritten. Nothing is guaranteed durable before a flush.
  • Fixed-size volumes. 256 blocks each; no volume_blocks manifest key; volumes are never freed.
  • One key release per boot. In the attested flow the host says bye after releasing the key, so a disk restarted later stays locked until the next boot.
  • One CPU, no IPC priorities, messages copied (no memory lending).

Test case format

Each row of CASES in tests/run.sh:

"name | app | user features | kernel features | make variables | expected status | expected text"

Expected text is a fixed string; with re:, a Perl regex over the whole output (grep -Pz, so [\s\S]* spans lines; use lookaheads for order-independent matches; avoid quotes); with cmd:, a shell command that reads the output on stdin and must succeed.

21Recipes#

21.1Add a user program#

  1. Copy user/hello/ to user/<name>/ (keep build.rs: it applies user/linker.ld). Rename the package and [[bin]].
  2. Write src/main.rs: 
    #![no_std]
#![no_main]

use vanir_user::println;

vanir_user::entry!(main);

fn main() -> u64 {
    println!("<name>: hello");
    0 // exit code
}
  3. Add "user/<name>" to members in the root Cargo.toml and <name> to USER_PROGS in the Makefile (that also makes it a boot module and signs it).
  4. Reference it from a manifest: program = "<name>".

21.2Add a test case#

  1. Add a manifest in tests/apps/ if no existing one fits.
  2. Put test-only behaviour behind a cargo feature in the program's Cargo.toml, with a comment saying what it tests.
  3. Add a row to CASES in tests/run.sh, after the cases whose state it depends on.
  4. Run it alone (ONLY='^name$' make test), then break the protection on purpose and confirm the case fails, then restore and run both full suites.
  5. Add it to 19 and, for a protection, 15.

21.3Add a syscall#

  1. Pick an unused number; add SYS_<NAME> to kernel/src/syscall.rs and a dispatch arm.
  2. Implement the handler (in kernel/src/process.rs if it touches the task table). Read arguments from the TrapFrame; write results to rax/rdx/rsi. Validate every user pointer with the address space's check_range and copy through usercopy. Never block inside the handler: mark the task blocked and switch.
  3. Add the same constant and a wrapper to user/lib/src/lib.rs.
  4. Restrict privileged calls to the right task (as restart is supervisor-only) and return NOT_ALLOWED otherwise.
  5. Document it in 14.

21.4Add a kernel or storage event#

  1. Kernel event: a constant in kernel/src/events.rs (document what a, b, c hold), events::log(...) at the control point, the same constant in user/lib events, and a format arm in event_line in user/telemetry.
  2. Storage event: a kind constant in user/lib telemetry, a format arm in storage_line, and self.event(kind, block, name) in user/storage.
  3. Check it with tools/host-agent.py - --quiet --check --expect <event>=1 in a cmd: test.

21.5Add a device kind or driver#

  1. Add (name, vendor, &[device ids]) to KINDS in kernel/src/pci_kinds.rs (shared with build.rs, which validates manifests).
  2. Add the QEMU device to QEMU_FLAGS (behind a variable, as DISK is) with disable-legacy=on for virtio.
  3. Write the driver on user/virtio; take requests by IPC; handle NOTIFY_IRQ; use RECV_EXPECT_IRQ while work is in flight.
  4. Add a crash feature and a restart test, as virtio-blk/crash-after-10.

21.6Add a manifest key#

  1. Add it to known in kernel/build.rs, parse and validate it, and emit it in the generated Task literal.
  2. Add the field to Task in kernel/src/process.rs.
  3. Document it in apps/README.md and 7.

22Invariants#

Rules the code relies on. Breaking one is a bug even when the tests pass.

  1. Every commit passes the full suite under both TCG and KVM.
  2. Stable Rust only. No nightly features or -Z flags.
  3. The kernel never blocks mid-syscall. Waiting means saving registers, marking the task blocked, and writing results into its saved frame later.
  4. User pointers are untrusted. Range-checked and copied with fault recovery under SMAP; never dereferenced directly.
  5. Identity comes from the kernel. Servers decide who a client is with task_name(sender), never from message contents.
  6. W^X everywhere. No mapping is both writable and executable.
  7. Mechanism in the kernel, policy in tasks. Restart decisions belong to the supervisor; key decisions to keys/attest/the host.
  8. Default deny. No IPC without sends; no device without a grant; storage locked until keyed.
  9. Secrets stay out of git and out of images. keys/ is ignored; the storage master key is never on the disk.
  10. Crypto uses the portable backends. The --cfg flags in .cargo/config.toml select them; removing them makes rustc crash (SIGILL) on this target.
  11. The measured set is the source of truth. Kernel, manifest and task statements go into PCR 12; tools/expected-pcrs.py must compute the same value.
